# Day 02 - Modern Java Syntax: Records, Sealed Classes, Pattern Matching

> **Phase:** Java Foundations | **Date:** 2026-03-02 | **Code:** [`ModernJavaSyntax.java`](./ModernJavaSyntax.java) | **Runtime:** JDK 21+

## 1. Core Concepts

### Records (Java 16)
A record is a *transparent, shallowly immutable data carrier*. The compiler generates the canonical constructor, accessors, `equals/hashCode/toString` (all via `ObjectMethods` bootstrap + `invokedynamic`, not generated bytecode). Use the **compact constructor** for validation and defensive copies. Records cannot extend classes, cannot declare instance fields, but can implement interfaces, have static members and nested types.

### Sealed types (Java 17)
`sealed interface Shape permits Circle, Square` restricts the hierarchy. Each permitted subtype must be `final`, `sealed` or `non-sealed`. The compiler then knows the closed set, which enables **exhaustive `switch` without `default`** - adding a new subtype breaks compilation at every switch, which is exactly what you want in domain modelling (algebraic data types / sum types).

### Pattern matching (Java 16-21)
* `instanceof` patterns: `if (o instanceof String s && s.length() > 3)`.
* `switch` patterns with guards: `case Success s when s.latency() > 100 -> ...` (final in 21).
* **Record deconstruction patterns**, nestable: `case Add(Const(var a), Const(var b)) -> new Const(a + b)`.
* Dominance: a more general label may not precede a more specific one (compile error).

### Other modern features worth knowing
`var` (10), text blocks (15), switch expressions with `yield` (14), `Stream.toList()` (16), **sequenced collections** (21: `getFirst()`, `getLast()`, `reversed()`), unnamed patterns `_` (22+), `String.formatted`, `Objects.requireNonNullElse`.

### Why it matters for AI backends
Inference outcomes are naturally a sum type: `Success | Failure | Timeout`. Sealed + records makes the compiler enforce that every caller handles every outcome. Feature-expression trees, query ASTs and DSL interpreters get the same benefit.

## 2. Memory Architecture Breakdown

```
record Point(double x, double y)          Heap layout (compressed oops)
+------------------------------+          +-----------+------------+----+----+
| class Point (final, Record)  |   ==>    | mark 8B   | klass 4B   | x  | y  | = 32 B
| private final double x, y    |          +-----------+------------+----+----+
+------------------------------+
record Success(String m, double[] s, long t)  ->  [hdr][m ref]-->String  [s ref]-->double[] [t]
```
* Records are **shallowly** immutable: a `double[]` component is still mutable and `equals` compares array *references*. Clone in the compact constructor and in the accessor, or use `List<Double>`/a dedicated `Vector` type.
* `ObjectMethods` makes `hashCode` per-component via a MethodHandle chain; JIT inlines it, so records are as fast as hand-written classes.
* Sealed hierarchies are recorded in the `PermittedSubclasses` class-file attribute and verified at class load time.
* Pattern-matching switch compiles to `invokedynamic` `SwitchBootstraps.typeSwitch` - a type-test loop, not a chain of `instanceof` bytecodes; cost is small and optimisable.

## 3. Interview Edge Cases & Pitfalls

1. Record with array component: `equals`/`hashCode` use reference semantics - two logically equal records are unequal.
2. A compact constructor must not assign `this.field = ...`; it reassigns the *parameter* and the compiler copies it at the end.
3. Records can't be `abstract`, can't extend, but may implement a sealed interface - the idiomatic ADT combo.
4. Pattern `case Success s` before `case Success s when ...` is a dominance error: guards go first.
5. Adding a `permits` subtype in a different package requires a *module* (named) - or the same package in the unnamed module.
6. Deserialising a record bypasses the constructor? No - Java serialization of records *always* calls the canonical constructor, so validation is enforced.
7. A `switch` over a sealed type with missing case throws `MatchException` at runtime if the hierarchy changed after separate compilation.

## 4. Interview Q&A

**Q1. Are records fully immutable?**  
No - shallowly. Fields are final but referenced objects (arrays, `ArrayList`) may mutate. Defensive-copy in the compact constructor and accessors.

**Q2. When would you pick a sealed interface over an enum?**  
Enums have one instance per constant with identical shape. Sealed interfaces let each variant carry *different data* (`Success(scores)`, `Failure(reason)`), giving exhaustive pattern-matching on heterogeneous variants.

**Q3. How does exhaustive switch improve maintainability?**  
Adding a variant produces compile errors at every switch lacking it, so no silent fall-through to a `default` branch that hides a bug.

**Q4. Can a record have a custom `equals`?**  
Yes, but the contract must still hold; usually you just fix the component types (e.g. use `List<Double>` instead of `double[]`).

**Q5. What is the difference between `instanceof` pattern and a cast?**  
Pattern binds a flow-scoped variable only where the test is definitely true, eliminating redundant casts and `ClassCastException` risk; scoping follows `&&`, `!` and early-return rules.

**Q6. Do records have a performance advantage?**  
Not inherently - same layout as a final class. The advantage is correctness and brevity; escape analysis removes short-lived ones. Valhalla value classes will later remove the identity header.
